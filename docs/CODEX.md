# CODEX.md — работа с сессиями Codex CLI

recall не просто индексирует Claude Code — он видит и Codex CLI (OpenAI) как
второй тип сессий в том же индексе. Этот документ — справочник по механике:
где живут файлы, как устроен resume, как не заинжектить самому себе, и как
передать контекст из Claude в Codex руками одной команды.

Формат роллаутов подробно расписан в [codex-rollout-format.md](codex-rollout-format.md)
(строка за строкой, эволюция версий, парсинг) — здесь только то, что нужно
для повседневной работы.

## Где живут сессии

`~/.codex/sessions/YYYY/MM/DD/rollout-<timestamp>-<uuid>.jsonl` (+ 3 legacy-файла
прямо в корне, старый формат без вложенности по датам). `<uuid>` в имени
файла == `session_id`. Строка 1 = `session_meta`: `session_id`, `cwd`,
`originator`, `cli_version`. Юзер-текст — в `event_msg` с
`payload.type == "user_message"`, уже чистый, без служебных вставок.

`originator` различает две породы:
- `"codex-tui"` — интерактивная сессия юзера, попадает в реестр recall;
- `"codex_exec"` — батч-вызов, аналог субагента; **в реестр не идёт**, и это
  норма, не баг.

## Resume-семантика

`codex resume <session-id>` дописывает в ТОТ ЖЕ rollout-файл — id не меняется.
Каждый resume/рестарт добавляет в файл ещё одну строку `session_meta`
(проверено на живых данных: один roll-аут содержал 3 `session_meta` подряд с
непрерывной лентой `user_message` между ними, id один и тот же на всех).

Следствия:
- Контекст при резюме сохраняется полностью — юзер ничего не теряет.
- Никаких «цепочек» файлов нет: одна сессия = один файл, сколько бы раз её ни
  резюмили. Несколько `session_meta` внутри файла — это просто маркеры
  рестартов той же сессии, а не разные сессии.
- Чтобы продолжить сессию — резюмить **её же** id, тот, что был всегда.

## Живость и окна

Три правила, каждое выстрадано на практике:

1. **Проверять живость — только `pgrep -fl codex`.** `ps aux` под сандбоксом
   Claude Code врёт (показывал 0 процессов при реально живом codex).
2. **Искать окно iTerm — по tty процесса, не перебором contents.**
   `ps -eo pid,tty,command | grep codex` → взять tty → найти iTerm-сессию с
   этим tty. Перебор окон по ключевым словам — ловушка: своё же окно
   матчится первым, инжект прилетает бумерангом самому себе.
3. **Инжект текста в TUI кодекса не сабмитится сам.** `iTerm write text`
   приходит как bracketed paste — Codex TUI ждёт реальный key-event для
   сабмита (System Events key code 36, нужен грант Accessibility) или руки
   юзера. «Написанный» текст в поле ввода — это ещё не отправленный текст.

Перед `codex resume` мёртвой (казалось бы) сессии — обязательно перепроверить
`pgrep` + peek окна. Мёртвый TUI на экране выглядит неотличимо от живого
(застывший скроллбек) — если ошибиться, получится два TUI в одном cwd.

## Как recall видит Codex

recall индексирует непустые `codex-tui` роллауты за последние 30 дней (кап
50 за прогон `sweep`):

- строка индекса: `<id13> <время> <проект> [new] <задача> #codex`;
- `id13` — первые 13 символов uuid из имени файла с дефисом, например
  `019f2adc-c5cc` (не путать с id8 у Claude-сессий — разная длина сигнализирует
  разный тип);
- LLM-карточек для Codex нет — только дешёвая строка `[new]` без вызова модели;
- `⚡LIVE` работает так же, как у Claude-сессий: живой codex-процесс + свежий
  mtime роллаута;
- архив: клоны роллаутов уезжают в `~/backups/claude-transcripts/codex/`
  (та же защита от потери транскриптов, что и для Claude);
- команды:
  ```bash
  recall find #codex          # найти сессии codex в общем индексе
  recall cmd <id13>           # -> cd <cwd> && codex resume <полный-id>
  ```

`recall cmd` для Codex не запускает окно сам — только печатает команду
(в отличие от `recall open` у Claude). Открыть окно самому — см. `to-codex --spawn`
ниже.

## Транзишн-ритуал: передать контекст из Claude в Codex

Механика команды (сам ритуал по шагам — в `skill/SKILL.md`, секция
«Codex-сессии»):

```bash
recall to-codex <dir> [--brief FILE | --task "текст"] [--spawn|--print]
```

- Пишет `<dir>/CODEX_HANDOFF.md` (шаблон ниже) — единственный канал передачи
  контекста, Codex ничего не видит из памяти Claude.
- Если в `<dir>` нет `AGENTS.md` — создаёт минимальный (шаблон ниже). Если
  `AGENTS.md` уже есть — не трогает его.
- `--spawn` — поднимает `codex` в новом окне iTerm в `<dir>`.
- `--print` — просто печатает, что было бы написано, без изменений на диске.

## Чего у Codex нет

- Нет доступа к Telegram/MCP-коннекторам Claude Code.
- Нет доступа к памяти Claude (`~/.claude/*`, recall-индексу, recap-карточкам).
- Весь контекст передаётся ТОЛЬКО файлами в рабочей папке — `CODEX_HANDOFF.md`,
  `AGENTS.md`, обычные файлы проекта.

Codex автоматически читает `AGENTS.md` из cwd при старте (это его нативная
конвенция, не изобретение recall) — поэтому хендофф пишется именно туда, а не
передаётся текстом в промпте.

## Шаблон CODEX_HANDOFF.md

```markdown
# Handoff: <краткое имя задачи>

## Задача
<что нужно сделать, своими словами, без воды>

## Сделано
- <пункт>
- <пункт>

## В работе
<что начато, но не закончено — конкретно, не «почти всё»>

## Дальше
- <шаг 1>
- <шаг 2>

## Гочи
- <грабли, на которые уже наступили — чтобы не наступать снова>

## Пути
- репо: <path>
- ключевые файлы: <path, path>
```

## Шаблон минимального AGENTS.md

Создаётся только если файла ещё нет — существующий `to-codex` не трогает.

```markdown
# AGENTS.md

Контекст задачи и текущее состояние — см. `CODEX_HANDOFF.md` в этой папке.

## Правила
- Секреты (пароли, токены, ключи) не коммитить в git и не класть в файлы.
- <жёсткие запреты этого проекта, если есть — отдельным пунктом каждый>

## Scope
<что можно менять; если scope нужно ограничить строго — фиксировать
флагами/валидацией в данных, а не только текстом здесь>
```
